# 文書の管理方針

## 管理する場所

| 内容 | 管理先 |
| --- | --- |
| 要求・変更提案、その背景や議論 | GitHub Issue |
| 合意済みの要件と受入条件 | `docs/requirements/` |
| 決まったコマンド構文・出力・保存形式などの仕様 | `docs/specifications/` 以下へ、決定時に追加する |
| 要件一覧と共通用語 | `docs/requirements.md` |
| 確認中の質問や、合意前の作業メモ | リポジトリ外。Git管理の対象にしない |

独立した要求仕様書は作らない。
各要件ファイルには、その要件が必要な理由として「要求」欄を残す。
Issueで扱う提案・議論の全文を複製せず、採用した内容に必要な背景を簡潔にまとめる。
要件・仕様を決定したら対応する文書を更新し、Issueと文書から相互に参照できるようにする。
質問への回答がまだない内容や、AIの提案だけの内容を、決定済みの要件・仕様に混ぜない。

## ファイルの単位

当面は一つの要件ごとに、要求・要件・受入条件を1ファイルへまとめる。
一つの要件が大きくなった場合は、概要を入口として詳細を別ファイルへ分ける。
仕様も機能や操作の単位で分割し、対応する要件へのリンクを持たせる。
一覧にはリンクを載せ、同じ要件の正本を複数作らない。
受入条件は要件ファイル内の箇条書きで扱う。

## このCLI自身への適用

本CLIで、このリポジトリの文書も管理する。
要件・仕様・対応する実装・テストを、意味のある関連グループとして登録する。

例えば、確認状態の判定を扱うグループには、次のファイルを関連付ける。

- [内容に基づく確認状態](../requirements/confirmation-state.md)
- 対応する詳細仕様
- 対応する判定実装
- その振る舞いを検証するテスト

このグループには「確認状態の要件・仕様・判定実装・テストの間で、変更時に整合性を確認するため」という理由を残す。
いずれかの内容が変われば、他の構成ファイルを含めて確認する。
必要な修正を終えた後に改めて検査し、その結果の組み合わせを確認して記録する。
文書分割や移動でグループ構成を変更した場合も、登録を更新して確認し直す。

受入条件に対応するテストコードも同じ関連グループへ含める。
条件を満たしているかは、テスト内容の確認と実行結果で判断する。
本CLIは変更影響と確認記録を管理し、テストの合格や要件の充足を自動保証しない。

CLI本体の登録・検査・確認操作が実装された段階で、自身の文書へ適用する。
その後、CIから同じ検査を実行できるようにする。
