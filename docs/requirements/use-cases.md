# ユースケース

合意済みの要件に対する代表的な利用の流れを記載する。
確認状態は「確認済み／未確認」の2つで扱う。

## UC-001. 仕様変更による実装確認

1. Markdownと複数のソースコードが関連付けられている。
2. 開発者がMarkdownを変更する。
3. ツールがハッシュの違いを検出し、グループを未確認として提示する。
4. 開発者は、確認が必要な理由と全構成ファイルを参照し、必要な実装を変更する。
5. 最終的な内容を改めて検査し、グループ全体の整合性を確認する。
6. その検査結果を対象に、明示的な確認操作で確認済みにする。検査後に内容が変わっていれば確認は失敗する。

## UC-002. 実装変更による仕様確認

1. Markdownとソースコードが関連付けられている。
2. 開発者がソースコードを変更する。
3. ツールが、関連Markdownを含むグループの確認が必要であることを提示する。
4. Markdownの変更が不要であれば、編集せずに明示的な確認操作で完了する。

## UC-003. ソースコード間の整合性管理

1. `api.ts` と `client.ts` が関連付けられている。
2. `api.ts` を変更すると、`client.ts` を含むグループが確認対象となる。
3. 必要に応じて `client.ts` を変更する。
4. 最終的な両ファイルを検査し、整合性を確認する。
5. その検査結果を対象に、明示的な確認操作で確認済みにする。

`client.ts` を起点に変更した場合も同様に成立する。

## UC-004. 複数ファイルの関連管理

A・B・Cを一つのグループとして登録する。
Aが変わればB・Cも確認対象になる。Bも変更した場合はA・Cを含む全体を確認する。
最後に確認した組み合わせと異なる限り、全ファイルを編集しただけでは確認済みにならない。
修正後に改めて検査し、その組み合わせについて全体を確認して記録する。

## UC-005. 複数グループに所属するファイル

- Group-1：A・B
- Group-2：B・C

Aだけを変更するとGroup-1が未確認になる。Group-2には伝播しない。
Bを変更すると両グループが未確認になる。
Group-1だけを確認しても、Group-2は未確認のままである。

## UC-006. 確認後の再変更

1. A・Bを明示的に確認済みにする。
2. Aを変更すると、グループは未確認になる。
3. 現在の内容を検査してグループ全体を確認し、その検査結果を対象に明示的な確認操作を行う。
4. その後Bを変更すると、再び未確認になる。

再確認する前に全ファイルを最後に確認した内容へ戻した場合は、既存の記録と一致するため確認済みに戻る。

## UC-007. CIでのマージ防止

1. 開発者またはAIエージェントがファイルを変更し、PRを作成する。
2. CIが、その時点の実ファイルと管理ファイルを使って非対話で検査する。
3. 未確認や検査不能があれば、検査は非ゼロ終了しCIを失敗させる。
4. 開発者が対象を確認し、必要な修正を行う。
5. 最終的な内容を再検査し、その結果を対象として確認操作を実行する。
6. 確認記録と修正したファイルを共有する。
7. 全グループが現在の内容で確認済みになれば、CIの検査は成功する。

Gitはこのユースケースで利用する環境であり、CLI本体の実行依存ではない。
